系统健康

系统健康把配置、115、路径、Emby、302 网关、Docker 和网络连通性拆成可重试的检查项。它用于定位故障边界，不替代任务记录和系统运行日志。

适用场景与前置条件

  • 部署、迁移、升级后做整体验收；或仪表盘、整理、STRM、通知、网关出现异常时使用。
  • 健康检查会读取当前配置并访问外部服务/Emby/115；检查前确保你有权限查看这些运行状态。
  • 网络检测不是单纯 ping，而是从 CineChill 后端逐个发起 HTTP/HTTPS 目标检测。

运行健康检查

  1. 从任意后台页面顶部工具栏点击“健康检查”，打开截图所示的检查弹层；不要把它当成必须从侧边栏进入的独立页面。
  2. 等待检查逐项完成；每项可单独点击重新检查。
  3. 先看总览状态：有 error 时整体为异常；只有 warning 时整体为提醒；disabled 表示该能力未启用。
  4. 修复对应配置/路径后，只重试对应项，再重新运行整体验证。

检查项怎么看

  • 配置文件：读取已存在的 JSON；缺失文件会按默认值处理，不等于系统损坏。
  • 115 Cookie：实际探测 Cookie 是否有效，并显示账号/客户端摘要；依赖 Cookie 的其他项会受它影响。
  • 115 标准目录：检查远程根目录及媒体、秒传、失败、转存、重复、洗版目录是否存在且 CID 匹配。
  • 媒体库本地路径 / 真实库本地路径：检查目录存在、可读、可写，并创建后立即删除临时探针文件。
  • Emby API：使用配置的地址和 API Key 请求 Emby 系统信息，超时或认证失败会标为异常。
  • 302 网关：检查配置的网关端口是否在 CineChill 运行环境的本机监听。
  • Docker Socket：检查 Socket、当前容器、端口映射和 Compose 状态；未挂载时会显示未启用。

网络连通性检测

  1. 点击顶部工具栏“网络检测”，打开网络检测弹层。
  2. 等待目标逐项检测，查看目标主机、状态、HTTP 状态、延迟和错误信息。
  3. 先重试具体失败目标，再根据目标所属组排查：TMDB/图片、豆瓣/发现源、Telegram/企业微信、115、Docker Hub/GitHub/PyPI 等。
  4. 网络结果会保留最近一次记录；修复代理或 DNS 后重新检测，不要只根据旧结果判断。

首次验证标准

  • 配置文件正常，115 Cookie 和标准目录正常。
  • 媒体库本地路径与真实库路径可读写。
  • Emby API 正常，网关端口按实际使用情况监听；不使用 Docker 时 Docker 项可以是未启用。
  • 与当前业务有关的网络目标正常；不需要的可选第三方目标失败，不应被误判为核心链路故障。
  • 完成后运行一个小任务，再用系统运行日志确认没有新的同类错误。

先按这个顺序判断

  1. 先看总览状态和失败项目名称，记录检查时间、错误摘要和对应页面。
  2. 优先修复上游依赖：配置文件 → 115 Cookie/标准目录 → 本地路径 → Emby API → 网关 → Docker/网络。
  3. 每次只点击失败项目自己的“重试”，通过后再运行一个小任务，最后重新做整体验收。
  4. 如果健康检查正常但业务仍失败，转到整理记录、115 任务历史、MoviePilot 任务或系统运行日志，不要继续重复健康检查。

常见问题：检查项失败后怎么处理

下面每项都按“你会看到什么 → 先做什么 → 通过标准”写。不要一次修改多个配置，否则无法判断是哪一步恢复了。

1. 配置文件异常

你会看到：配置文件检查为 error，登录、任务或外部服务配置突然消失。

  1. 先停止自动整理、自动封面、RSS 和上传任务，避免系统继续写入配置。
  2. 执行 docker inspect cinechill，确认 /app/config 映射到预期宿主机目录；不要在容器内临时改文件。
  3. 打开系统运行日志，记录具体 JSON 文件名和解析错误；只修复该文件，不要直接删除整个配置目录。
  4. 修复后刷新健康检查，再登录并打开服务器配置，确认 Emby、115 和任务状态仍存在。

通过标准：配置文件检查正常，已有账号和任务没有被清空，页面可以继续读取配置。

2. 115 Cookie 或标准目录异常

你会看到：Cookie 无效、标准目录找不到，或媒体/秒传/失败目录 CID 检查失败。

  1. 回“服务器配置”重新扫码或粘贴完整 Cookie，去掉首尾空格，先点击“测试连接”。
  2. 测试显示 Cookie 有效后点击“保存配置”，让后端重新解析远程根目录；不要手工改 CID。
  3. 如果 Cookie 有效但保存失败，检查 /app/config 和本地媒体根目录可写，再看系统日志第一条错误。
  4. 标准目录全部正常后，再去 115 秒传选择具体目标目录，最后才恢复 RSS、上传或整理任务。

通过标准：Cookie 有效，媒体、秒传、失败、转存、重复和洗版目录都能识别。

3. 媒体库本地路径或真实库路径不可写

你会看到：目录不存在、只读、写探针失败，整理或 STRM 任务无法继续。

  1. 用 docker inspect cinechill 对照宿主机源路径和容器目标路径；Emby 和 CineChill 的媒体映射必须指向同一宿主机目录。
  2. 在容器内检查：docker exec cinechill sh -c 'ls -ld /media /app/config'；确认目录不是空的错误挂载。
  3. 检查宿主机属主、权限和挂载模式；只读挂载或容器用户无写权限时，健康检查会在创建探针时失败。
  4. 修正后重新创建容器，再单独重试路径检查；不要只刷新浏览器。

通过标准：目录存在、可读、可写，健康检查的探针可以创建并删除。

4. Emby API 异常

你会看到：Emby API 超时、401/403，或健康检查无法读取系统信息和媒体库数量。

  1. 回“服务器配置”核对 Emby 地址；不要填 CineChill 容器内的 localhost 或 127.0.0.1。
  2. 401/403 重新核对 API Key 权限；地址能打开不代表 API Key 能读取媒体库。
  3. 容器网络无法访问时，从 CineChill 运行环境检查服务名、NAS 地址、DNS 和防火墙。
  4. 服务器配置测试成功后，再单独重试 Emby API，最后刷新媒体库或运行一个小整理任务。

通过标准：能读取 Emby 系统信息和媒体库数量，整理或封面页面能正常加载媒体库。

5. 302 网关异常

你会看到：网关未监听、STRM 地址打不开，或反向代理返回 502。

  1. 执行 docker compose ps 和 docker port cinechill，确认宿主机端口确实发布。
  2. 对照服务器配置中的反代端口、Compose 左侧端口和反向代理上游端口；三处必须一致。
  3. 直连主机端口验证：直连正常、域名不通时查反向代理和防火墙；直连也不通时查容器日志和端口占用。
  4. 修复后重新创建容器，打开一条 STRM 实际播放验证，不要只看端口检查变绿。

通过标准：网关在 CineChill 运行环境监听，反向代理能访问，STRM 地址可打开并能播放。

6. Docker Socket 或 Compose 状态异常

你会看到：Docker 项显示未启用、读取不到容器或 Compose 状态为空。

  1. 确认 Compose 有 /var/run/docker.sock:/var/run/docker.sock 挂载，并重新创建 CineChill 容器。
  2. 如果需要 Compose 写回，再确认 Compose 文件目录也挂载到容器内且可写；只挂 Socket 不代表可以修改文件。
  3. 不使用 Docker 管理功能时，该项显示 disabled 可以接受，不要为了让它变绿而增加高权限挂载。
  4. 恢复挂载后只重试 Docker 项，再到 Docker 管理页读取当前容器和日志。

通过标准：需要 Docker 管理时能读取容器、端口和 Compose；不使用时明确显示未启用且核心媒体链路正常。

7. 网络连通性异常

你会看到：TMDB、图片、115、GitHub、Docker Hub 或其他目标超时、DNS 失败或 HTTP 状态异常。

  1. 先看失败目标的主机、状态码和延迟，判断是全部外网失败还是单个目标失败。
  2. 全部外网失败：检查代理、DNS、默认路由和容器网络；只有一个目标失败：检查目标服务、域名或账号限制。
  3. 修改代理后只重试失败目标，再回 TMDB/RSS/图片等实际业务页面验证，健康检查通过不等于业务请求一定成功。
  4. 确认无误后恢复自动任务；不要在网络不稳定时同时运行全量刮削、RSS 和上传。

通过标准：当前业务需要的目标可以从 CineChill 运行环境访问，且实际小任务不再产生同类网络错误。
