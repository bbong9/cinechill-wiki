Docker 管理

Docker 管理页通过 Docker Socket读取容器和镜像状态，并提供启动、停止、重启、日志、更新、自动策略和镜像清理操作。它是运维控制面，不是无风险的监控面板。

本页怎么用

Docker 管理：实际操作指南

Docker 管理是容器控制面。先确认 Docker Socket 和 Compose 路径可用，再执行单个容器操作；更新镜像前不要直接点击全量写回。

按这个顺序操作

  1. 确认 Compose 挂载了 /var/run/docker.sock；需要写入 Compose 时再挂载可写项目目录，并确保容器内绝对路径一致。
  2. 打开页面先刷新容器列表，选择一个容器查看状态、端口、挂载和环境变量，再执行启动/停止/重启。
  3. 查看日志时先按容器和时间定位错误；不要在没有记录的情况下连续重启。
  4. 更新镜像前记录当前镜像标签和容器配置，先拉取并更新一个非关键容器，再观察日志和健康状态。
  5. 写回 Compose 或清理镜像前确认项目路径、目标容器和磁盘空间；操作后用 docker compose ps 和页面状态双重确认。

完成后看什么

  • 页面能读取容器状态和日志，单个容器操作后状态与 Docker CLI 一致。
  • 更新后容器重新运行、配置挂载仍在、管理端和核心功能可访问。

小白最容易错在哪里

  • 页面显示 Docker 不可用：检查 Socket 挂载和权限，而不是重装容器。
  • 更新镜像后配置丢失：检查 config 挂载和 Compose 写回路径，配置目录必须持久化。

适用场景与前置条件

  • 部署时挂载 /var/run/docker.sock，否则页面会显示 Docker 不可用。
  • 只在自有 NAS/服务器使用；Docker Socket 等同于授予应用较高的主机容器控制能力。
  • 如果需要“写入 Compose”，还要把 Compose 项目文件以可写方式挂载到容器内的同一绝对路径。

第一次使用

  1. 从控制台左侧直接点击“Docker 管理”，确认 Docker 版本、架构、容器数和镜像数能显示。它与“Emby 任务中心”并列，不属于“系统配置”分组。
  2. 在“容器”视图按全部、运行中、已停止、有更新筛选，或搜索容器名、镜像和端口。
  3. 打开目标容器详情，先看当前镜像、更新目标、Compose 状态、端口、挂载、CPU/内存和策略。
  4. 需要排查时点击“查看日志”；页面读取最近一段容器日志，可手动刷新。
  5. 启动/停止/重启/删除前确认目标容器；更新前确认配置目录和回滚镜像仍在。

容器操作与字段含义

  • 当前镜像：容器实际使用的镜像引用。
  • 更新目标：本页检查/更新时使用的镜像引用，可在“修改镜像版本”中编辑。
  • Compose 镜像：从 Compose 文件解析出的 image；只有 Compose 可定位且可写时才能“写入 Compose”。
  • 端口映射：宿主机端口到容器端口的发布关系；Host 网络或未发布端口会显示相应说明。
  • 自动更新：保存该容器的自动更新策略；“忽略更新”会跳过检查和自动更新。
  • 自动重启：可按时间或内存持续超阈值触发，配置前确认不会与主机/Compose 重启策略冲突。

镜像管理

  1. 切换到“镜像管理”，可按镜像名或 Tag 搜索。
  2. “拉取镜像”只拉取镜像，不会自动替换正在运行的容器。
  3. “删除镜像”需要确认；仍被容器占用时 Docker 会拒绝。
  4. “清理未使用”和“清理无 Tag”会调用 Docker 清理操作，先确认本机没有依赖这些镜像的回滚需求。
  5. Docker Hub 私有/限流场景可在“DockerHub 拉取认证”保存用户名和 Access Token；页面不会回显 Token。

更新、写回与首次验证

  1. 先点击“检查更新”，等待逐镜像结果；失败的检查项要单独看详情。
  2. 更新单个容器时确认镜像引用有效，再确认更新对话框。
  3. 如果容器由 Compose 管理，先用“修改镜像版本”保存目标，再按需点击“写入 Compose”。写回前后端会创建带时间戳的 .bak-YYYYMMDDHHMMSS 备份。
  4. 更新任务可能经历拉取、重建和重启；如果更新的是当前 CineChill 容器，浏览器短暂断开是预期现象。
  5. 完成后刷新 Docker 管理、访问 CineChill、检查 /api/version、系统健康和关键任务。

失败排查

  • Docker 不可用：检查 Socket 是否挂载、Docker daemon 是否运行，以及容器是否有权限读取 Socket。
  • Compose 写回按钮不可用：确认容器确实由 Compose 管理、Compose 文件已挂载、路径一致且可写。
  • 镜像检查失败：检查外部网络、代理、Docker Hub 认证和镜像引用；不要把检查失败当作“没有更新”。
  • 更新后容器未起来：查看容器日志和 Compose 状态，必要时把 Compose image 改回旧标签并执行 docker compose up -d。
  • UI 不可用时可用 docker ps、docker inspect <容器名>、docker logs --tail 200 <容器名> 读取基础状态。

备份、回滚与安全

  • 更新前备份 CineChill/Emby 的配置目录、Compose 文件和关键挂载；不要先清理旧镜像。
  • 回滚优先使用上一个已验证镜像标签；Compose 写回产生的 .bak-* 文件可用于恢复原 image 行。
  • 删除容器不会自动删除镜像，但会中断服务；删除镜像和清理未使用镜像都可能影响后续回滚。
  • Docker Hub 用户名和 Access Token 只在私有环境保存；不要把 Token 写入 Wiki、Compose 或截图。

按操作排查：Docker 管理

页面显示未启用或读不到容器

  1. 确认 Compose 挂载了 /var/run/docker.sock:/var/run/docker.sock，并重新创建 CineChill 容器。
  2. 检查 Socket 权限和容器日志；没有 Socket 时，核心媒体整理不一定受影响，但 Docker 管理功能不可用。
  3. 刷新页面确认能看到当前容器，先不要执行更新或清理。

启动、停止、重启或日志操作失败

  1. 记录容器名和操作时间，去系统运行日志及 docker logs --tail 200 <页面显示的容器名> 查第一条错误。
  2. 确认目标容器名称不是旧服务名，且 Docker daemon 正常；页面操作成功不代表应用已经健康。
  3. 修复后只操作一个测试容器，确认状态和日志恢复后再批量处理。

更新镜像后服务异常

  1. 先确认镜像拉取成功、容器已重建，再检查端口、挂载和环境变量是否仍存在。
  2. 不要立即清理旧镜像；先确认 CineChill、Emby、115 测试和小样本任务均正常。
  3. Compose 写回失败时检查 Compose 文件挂载和权限，不要手工删掉正在运行的配置文件。
